# US-013：履約成功通知 測試

**作為** 開發者  
**我想要** 先有會失敗的履約成功通知測試  
**以便** 三種方案與續訂各在履約提交後恰一則通知

**輸入格式**：
- spec §2 Story 5 type 表與「不建通知」清單
- `app/api/payments/ecpay/webhook/route.ts`（`unlockIfLocked`、`fulfill_points_pack_order`、`activate_subscription_from_order`）、`period-webhook/route.ts`（`apply_subscription_period_event`）

**輸出格式**：
- `webhook/route.test.ts`、`period-webhook/route.test.ts` 新增案例

**驗收條件**：
- [ ] 聚焦測試因功能尚未實作而預期紅燈（失敗原因是功能缺失，不是語法或 import 錯誤）
- [ ] S5-2：終身成功且 `access_status=unlocked` → 恰一則 `unlock_completed`（`unlock:{order_id}`）
- [ ] S5-2：點數包 RPC 回 `credited` → 恰一則 `credit_completed`（`credit:{order_id}`）
- [ ] S5-2：月繳 RPC 回 `activated` → 恰一則 `subscription_active`，key 為 `sub:{first_success 事件 id}`（事件 id 以該事件的 `idempotency_key` 另查）
- [ ] S5-2：上述三種 Webhook 再送 → 通知列數不變
- [ ] S5-4：`renewal_success` 寫入後 → 恰一則 `subscription_active`（`sub:{event_id}`）；重送不增加
- [ ] 不建通知：`SimulatePaid=1`、驗簽失敗、`first_duplicate`、`payment_failed`、`activate_subscription_from_order` 回 `conflict`
- [ ] S5-5：通知 insert 失敗 → 權益保持已交付、訂單仍 paid、回應仍 `1|OK`

**測試策略**：Test-First 測試準備  
> 理由：寫入點與 key 規則明確，適合先寫紅燈。
