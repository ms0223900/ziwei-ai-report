# US-003：建立訂閱表遷移

**作為** 系統  
**我想要** 建立 `subscriptions`、`subscription_events` 兩張表並設定 RLS  
**以便** 訂閱狀態與事件有持久來源，且只能由後端寫入

**輸入格式**：
- spec §4 DB Schema
- RLS 與 revoke 比照 `supabase/migrations/20260918000000_create_orders.sql`

**輸出格式**：
- `supabase/migrations/20260925000000_subscriptions.sql`
- `supabase/migrations/subscriptions.migration.test.ts`（比照既有 `*.migration.test.ts`，檢查 SQL 內容）

**驗收條件**：
- [ ] `subscriptions` 欄位：`plan_id text not null`、`order_id references orders(id)`、`user_id` 為 unique 並 `on delete cascade`、`merchant_trade_no not null unique`；`status` 的 check 只允許 `active|past_due|cancelled|expired`；起訖時間 `not null`；有 updated_at trigger
- [ ] `subscription_events` 欄位：`subscription_id` 與 `user_id` 皆 `on delete cascade`；`idempotency_key not null unique`；`event_type` 的 check 允許 `first_success|first_duplicate|renewal_success|payment_failed|cancelled|expired`；另有 `gwsr`、`total_success_times`、`rtn_code`；`processed_at not null`
- [ ] 兩張表都啟用 RLS：authenticated 只能 select 自己的列；anon／authenticated 不能 insert／update／delete
- [ ] 不改 `orders`、`profiles` 的結構
- [ ] migration 測試通過
- [ ] 已套用至 Supabase。套用後以 authenticated 身分實測 S11-1：對兩張表 insert／update 都被拒，並把結果貼進驗收說明

**測試策略**：Test-After  
> 理由：驗收靠遷移內容與套用後實測，不適合先寫單元測試。

**優先級**：P0  
**相關功能**：Story 11；spec §4  
**依賴關係**：無
